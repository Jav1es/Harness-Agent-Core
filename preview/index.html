核心案例 · Harness Engineering

Harness-Agent-Core

具备确定性守卫与自愈反馈的多智能体驾驭框架

不依赖特定大模型。通过代码级 Harness 架构，把开放式 AI 任务的 交付成功率从 70% 提升到 98%（作品集实验口径，见 §05）。

模型是马：快、有力、但不会自己认路。
Harness 是缰绳、马鞍与防护栏：它不产生动力，它决定这份动力往哪走、走多远、什么时候必须停。

缰绳不是装饰。它是唯一一条模型通往生产环境的合法路径—— 每一次工具调用都必须穿过中间的闸门。

01

为什么直接调大模型，总会翻车

把一个前沿模型接上业务系统，Demo 通常只要一个下午；把它变成能上生产的系统，通常要三个月——而且大部分时间不是在调模型，是在补它留下的坑。

下面五种失败模式不是模型「能力不够」，而是缺了一层结构化的驾驭层。换更强的模型不会让它们消失，只会让它们更贵。

划界「Harness」这个词已经有主了，先把关系说清楚

2026 年 Pydantic AI 发布了官方能力库 pydantic-ai-harness，也叫 Harness。名字撞了，这里主动交代：

它在做
给 agent 装能力——Coder、CodeMode、SubAgents、Memory、ToolGuardrail、spend limits，通过 Agent(capabilities=[...]) 组合进去。方向是加。
本作在做
约束 agent 别乱来——裁决这次调用能不能执行、失败了怎么带着现场回喂、重复失败什么时候熔断、什么时候挂起叫人。方向是减。
四个关键差异
工具治理：它的 ToolGuardrail 判「这个工具允不允许用」；本作判「这一次调用允不允许执行」——读 ctx 里的 scopes、金额、风险等级。
失败处理：它数重试次数与花费；本作用 semantic_fingerprint 判「这次失败是不是和上次同一个」——同一个就早停，不烧满 3 次。
人机协同：它支持运行中向人提问；本作在失败累计到阈值时熔断并挂起，保留完整失败现场再叫人。
评测：它无内置评测；本作把「确定性校验（零 LLM）」与「语义校验（LLM）」显式分成两层，不让后者污染前者。
一句实话
pydantic-ai-harness 比本作成熟得多，也有真实用户。本作不是它的替代品，也不基于它——两者解决的是相反方向的问题：一个在给 agent 加自由度，一个在给 agent 加约束。命名纯属巧合，本项目与 Pydantic AI 无任何关联。

  1. 幻觉当成事实Hallucination

    模型把「没查到」和「不存在」说成同一件事，输出一段格式完美、来源虚构的结论。人读起来毫无破绽，直到业务方拿去用了。

    confidence=0.93 source=None

  2. 越权调用工具Over-privileged Tool Call

    提示词注入让模型去调一个它本不该碰的写接口。工具描述是模型可读的文本，文本就能被改写；而权限判断如果也交给模型，等于没有判断。

    tool=settlement.write amount=8,400,000

  3. 格式漂移Schema Drift

    同一份 Prompt，今天返回合法 JSON，明天多一句「好的，以下是结果：」。下游解析器直接抛异常，而错误发生在离模型很远的地方。

    JSONDecodeError: Expecting value: line 1 column 1

  4. 死循环烧 TokenRetry Storm

    失败了重试、重试了还失败，没人设上限。一晚上跑掉一个月的额度，第二天早上你只拿到一堆看起来很像的失败日志。

    attempt=27 tokens_spent=1,284,900 status=retrying

  5. 不可观测No Trace

    出了问题只能靠翻聊天记录猜是哪一步坏的。没有 span、没有耗时、没有 token 账本，复盘就只能靠回忆。

    trace_id=<missing> spans=0
这五件事的共同点是：它们都不是模型的问题，是架构的问题。 模型负责「生成候选」，架构负责「决定什么能落地」。把这两件事混在一起做，才会出现「Demo 很惊艳、上线就事故」。 Harness 要做的，就是把后半句从模型手里拿回来，写进代码。

03

五大支柱：每一条都对应一段可审查的代码

这里不放理念，只放「这条原则在代码里长什么样」。五条支柱各自解决 §01 里的一种失败模式，且互不依赖—— 可以只上其中两条，收益依然成立。

  1. 01

    工具编排与上下文隔离Tool Orchestration

    MCP 负责「接得上」，Harness 负责「准不准接」。模型看到的只是工具描述，真正决定能不能执行的是代码里的白名单与权限表。

    • 每个工具在 TOOL_POLICY 里登记 scopes、是否产生副作用、金额上限
    • 模型输出的是 tool_call 申请，不是执行指令；未登记的工具直接抛 ToolDenied
    • 子任务跑在独立上下文里，只把摘要回传主图，避免上下文互相污染
    • 提示词注入能改描述，改不了 policy——这是白名单放在代码层而不是 Prompt 层的原因
    对应guard_tool_call()· 解决「越权调用工具」
  2. 02

    确定性硬约束守卫Deterministic Guardrails

    在非确定性输出与确定性业务系统之间，插一层纯函数过滤器。它必须是确定性的——用不确定的东西校验不确定的东西，等于没校验。

    • 三道关：JSON Schema（结构）→ 业务规则（语义）→ Linter（代码类产出）
    • 校验器零 LLM 调用、零随机、零网络，可单测、可复现、可进 CI
    • 不通过就返回 violations 列表，不写入任何业务系统——模型输出到这里只是一份提案
    • 规则库与代码分离，业务方改规则不用改引擎
    对应deterministic_validator()· 解决「格式漂移 / 幻觉当事实」
  3. 03

    自愈反馈循环Self-Correction & Feedback Loops

    失败不是终点，是下一轮的输入。关键是怎么把失败说清楚——直接把原始报错丢回去，模型往往去改无关的地方。

    • 捕获 error_stack：失败步骤、异常类型、关键栈帧、命中的规则编号
    • 结构化成修复指令：fix_hint 给方向，do_not_change 划边界
    • RAG 场景同理：召回率低于阈值时把「检索到了什么、漏了什么」一并回喂
    • 循环的终止条件是可执行的——自动化测试通过，不是模型说「我改好了」
    对应step_execution_with_harness()· 解决「改了还是错」
  4. 04

    熔断与人工介入网关Human-in-the-Loop & Circuit Breakers

    熔断不是「兜底让它通过」，是「在烧掉预算之前停手」。重试的边际收益下降极快，第 4 次之后基本是噪声。

    • max_retries 硬上限：耗尽即抛 CircuitOpen，不再追加 token
    • 高风险动作（外部写接口、大额修改）不重试，直接 挂起 + Webhook 通知等人批
    • 熔断状态分 CLOSED / OPEN 两态，页面 §04 有可交互演示
    • 人工审批回来的结果同样要过一遍校验，不因为「人批过」就跳过
    对应run_with_self_healing()· 解决「死循环烧 Token」
  5. 05

    全链路可观测与 CI 门禁Observability & CI Integration

    没有账本就没有优化。每次运行都要能回答三个问题：花了多少、慢在哪、这次和上次比是变好还是变坏。

    • 根 span 贯穿一次会话，子 span 覆盖 router / planner / tool / validator / responder
    • Token 与耗时按 span 记账，异常节点可以直接定位到具体环节
    • 智能体行为进 CI：30 题回归集每次 push 自动跑，断言不过即阻断合并
    • 门禁不只看「能不能跑通」，还断言检索准确率、引用准确率、拒答率
    对应ctx.trace + ci.yml· 解决「不可观测」

04

核心代码：四个函数，一条闭环

下面是从 harness_core.py 抽出的精简版（去掉业务细节，保留结构与注释）。 四个函数串起来就是完整链路：白名单 → 校验 → 回喂 → 熔断。基于 LangGraph 的状态机思想，工具层遵循 MCP 的隔离规范。

harness_core.py · 展示用精简版 
# harness_core.py —— Harness-Agent-Core 的核心闭环（展示用精简版）
# 设计前提：模型只产出「提案」，任何副作用都由 Harness 代码层决定是否执行。
from dataclasses import dataclass
import traceback

MAX_RETRIES = 3

# ── 工具白名单：不是「模型能调什么」，而是「Harness 允许执行什么」 ──────────
TOOL_POLICY = {
    "kb.search":        {"scopes": ["read"],  "side_effect": False},
    "jira.create":      {"scopes": ["write"], "side_effect": True, "approval": True},
    "settlement.write": {"scopes": ["write"], "side_effect": True, "approval": True,
                         "max_amount": 100_000},
}


class ToolDenied(Exception):
    """工具未授权。抛出即中止，不进入执行层。"""


class CircuitOpen(Exception):
    """重试额度耗尽。熔断，不再追加 token。"""


def guard_tool_call(name, args, ctx):
    """亮点 1 · 工具白名单鉴权：未授权工具在这里被拦下，永远到不了执行层。

    为什么白名单必须写在代码里而不是 Prompt 里：
    工具描述是模型可读的文本，文本就能被提示词注入改写；
    TOOL_POLICY 是代码常量，注入改不动它。
    """
    rule = TOOL_POLICY.get(name)
    if rule is None:                                  # ① 不在白名单
        raise ToolDenied(f"tool_not_allowed: {name}")
    if not ctx.granted_scopes.issuperset(rule["scopes"]):   # ② 越权
        raise ToolDenied(f"scope_missing: {name}")
    if rule.get("max_amount") and args.get("amount", 0) > rule["max_amount"]:
        raise ToolDenied(f"amount_over_limit: {name}")     # ③ 金额越界
    return rule


# ── 确定性校验：三道关，全部是纯函数，可单测、可复现、零随机 ────────────────
BUSINESS_RULES = [
    (lambda d: d.get("currency") in {"CNY", "USD"},        "schema.currency"),
    (lambda d: isinstance(d.get("amount"), (int, float)),  "schema.amount_type"),
    (lambda d: 0 < d["amount"] <= 100_000,                   "policy.amount_limit"),
]


def deterministic_validator(payload, schema):
    """亮点 2 · 业务规则 + Schema 校验：返回 violations，空列表表示放行。

    这里绝不调用 LLM。校验器本身必须是确定性的——
    用不确定的东西去校验不确定的东西，等于没有校验。
    """
    violations = []

    # ① 结构：JSON Schema
    violations += jsonschema_errors(payload, schema)   # 展示用占位实现

    # ② 语义：业务规则。单条规则异常不应炸掉整个校验器
    for rule, code in BUSINESS_RULES:
        try:
            if not rule(payload):
                violations.append(code)
        except Exception:
            violations.append(code + ".eval_error")

    # ③ 代码类产出额外跑 Lint
    if payload.get("patch"):
        violations += lint_patch(payload["patch"])     # 展示用占位实现

    return violations


def step_execution_with_harness(step, state, ctx):
    """亮点 3 · 失败捕获：把 error_stack 转成下一轮的纠错输入。

    注意回喂的不是错误原文，而是「结构化的失败现场」。
    原始 stack 直接丢回去，模型常常去改无关的地方。
    """
    try:
        out = step.invoke(state)                       # 模型 / 工具 / 子图
    except Exception as exc:
        state["error_stack"] = {
            "step": step.name,
            "type": type(exc).__name__,
            "message": str(exc),
            "trace": traceback.format_exc(limit=3),
        }
        state["status"] = "retryable"
        return state

    violations = deterministic_validator(out["payload"], out["schema"])
    if violations:
        state["error_stack"] = {
            "step": step.name,
            "type": "GateRejected",
            "violations": violations,
        }
        state["status"] = "retryable"
        return state

    state.update(out)
    state["status"] = "ok"
    return state


def build_repair_prompt(error_stack, history):
    """把失败现场压成一段「有边界」的纠错指令。

    do_not_change 是刻意加的：不给边界，模型会顺手重构，
    改动面从 6 行变成 60 行，回归风险直接翻倍。
    """
    return (
        "上一轮未通过校验，请只修复下列问题，不要改动其他文件。\n"
        f"失败步骤: {error_stack['step']}\n"
        f"失败原因: {error_stack.get('message') or error_stack.get('violations')}\n"
        f"错误栈:\n{error_stack.get('trace', '(无)')}\n"
        "约束: 不得修改公开 API 与数据库 schema；不得新增依赖。\n"
        "输出: 只给出 unified diff。"
    )


def run_with_self_healing(task, graph, ctx, max_retries=MAX_RETRIES):
    """亮点 4 · max_retries 熔断兜底：额度耗尽就停手，不再追加 token。

    熔断不是「让任务通过」，而是「在预算烧完之前止损」。
    实测第 4 次之后的成功率接近噪声，继续重试只是在给失败付费。
    """
    state = {"task": task, "attempt": 0, "history": []}

    for attempt in range(1, max_retries + 1):
        state["attempt"] = attempt
        state = graph.invoke(state)                    # LangGraph 状态机推进一步

        if state["status"] == "ok":
            ctx.trace.finish("self_healed" if attempt > 1 else "first_pass")
            return {"ok": True, "attempts": attempt, "state": state}

        if state["status"] == "needs_human":           # 高风险：挂起等人批
            ctx.webhook.notify(state["error_stack"])
            ctx.trace.finish("suspended")
            return {"ok": False, "reason": "human_approval_required",
                    "attempts": attempt}

        # 还有额度 → 把失败现场回喂下一轮
        state["history"].append(build_repair_prompt(state["error_stack"],
                                                    state["history"]))
        ctx.trace.span("retry", attempt=attempt, tokens=state.get("tokens", 0))

    # 额度耗尽 → 熔断
    ctx.trace.finish("circuit_open")
    raise CircuitOpen(
        f"max_retries={max_retries} exhausted; "
        f"tokens_spent={ctx.usage.total}; escalate_to_human=True"
    )
  • guard_tool_call() 白名单 + scope + 金额上限三重判断。未登记的工具直接抛异常，连执行层都进不去。
  • deterministic_validator() Schema → 业务规则 → Lint 三道关。纯函数、零 LLM 调用，可单测可进 CI。
  • step_execution_with_harness() 异常与校验失败都收敛成同一种 error_stack 结构，下游只处理一种形状。
  • run_with_self_healing() 循环有明确终点：通过、转人工、或熔断。不会出现「一直在重试」的第三种状态。

升级回喂的不是错误栈，是可修复的失败信号

以前的做法
把 traceback.format_exc() 原样丢回给模型。结果很稳定：模型会去改无关的地方——因为它看到的是一段自由文本，只能靠猜定位。
现在回喂什么
findings[] 列表，每条带 failed_gate（哪个闸门拒的）、offending_file:line（在哪）、severity（BLOCK 必须修 / WARN 只记录）、resolution_hint（怎么修）。模型不用猜。
为什么要有指纹
semantic_fingerprint 只对「失败本身」取哈希（闸门 + 位置 + 级别），不含 message 与栈。这样同一个失败重复出现时能识别出来：如果重试后指纹和上一轮相同，说明它根本没在修，立刻熔断，不等额度耗尽。3 次同样的失败和 3 次不同的失败，不该有相同的处理。

错误栈回喂时间线一次真实形态的自愈过程

  1. 1Error Stack测试跑飞
  2. 2Validator 拦截不放行
  3. 3Prompt 回喂带边界
  4. 4Retry只改 6 行

# 状态机（LangGraph StateGraph 的节点与边）

  plan ──▶ execute ──▶ validate ──▶ commit
             ▲            │
             │            ├── ok ────────────▶ done
             │            │
             └── retry ◀──┴── violations ──▶ (attempt < max) ──▶ 回喂后重跑
                                            └─ (attempt ≥ max) ──▶ circuit_open
                                                                  └─▶ 转人工

# 职责边界：谁能决定什么

  Frontier Model   ── 只能产出「候选」：tool_call 申请、patch、报告草稿
  Harness Layer    ── 决定「是否执行」：白名单、Schema、业务规则、额度、审批
  Enterprise Sys   ── 只接受已通过校验的、带 trace_id 的、可回滚的写入

# 为什么校验层必须与模型解耦

  1. 可测试   —— 纯函数，输入输出确定，能进 CI 当断言
  2. 可解释   —— 拦下来时能说清是哪条规则、哪个字段
  3. 可替换   —— 换模型、换供应商，校验层一行不用改
  4. 可审计   —— 规则库本身就是合规证据，不依赖模型当时的「想法」

口径这组数字是怎么来的，以及它不能说明什么

        

          
数据来源

          
项目实验 / 作品集口径。50 次测试由本人设计并执行，非客户项目、非第三方基准、非生产环境流量。


          
任务构成

          
代码生成与修复、结构化数据核对、报告撰写三类多步骤任务；每类都要求产出通过自动化断言（单测 / Schema / 规则）才算完成。


          
中断定义

          
任务在 max_retries 内未通过断言，或触发熔断转人工，记为一次中断。人工事后补救成功的不算自愈。


          
ok_with_warnings 不计入中断

          
只有 WARN 级发现（不影响交付的 lint 提示、风格问题）时，任务记为通过并记录告警，不算一次中断。早期版本把任何 violation 都当失败，会把「能交付但有小瑕疵」误算成中断率。


          
熔断分两种，都要计入中断

          
额度耗尽（circuit_open_exhausted）与失败重复（circuit_open_recurred）都记为中断。后者的价值在于它缩短了失败的持续时间，而不是避免了失败——这组数字衡量的是止损速度，不是成功率。


          
两个口径同源

          
中断率 32% 对应成功率 68%，四舍五入即 70%；中断率 < 2% 对应成功率 98%。开头那句「70% → 98%」与这里的「32% → < 2%」是同一组数据的两种表述，不是两组实验。


          
分母注意

          
50 次样本的最小分辨率是 2 个百分点：0 次中断才是 < 2%，1 次中断就是 2%（不满足 < 2%）。这组实验里中断数为 0，所以成功率写成保守值 98% 而不是 100%。样本量小是这套数字最主要的局限。


          
不适用范围

          
不能外推为「任意任务都能达到 98%」。任务越开放、断言越难写，收益越小——Harness 的上限取决于你能把验收标准写得多确定。


          
成本口径

          
自愈会多花 Token（本页演示链路约 2,270 tokens / 次），换的是人工返工时间。当人工成本低于 Token 成本时，这个交换不划算。

口径trace 数据从哪来，以及一个容易写反的地方

        

          
数据来源

          
本页展示的是演示数据，结构与 Opik（Apache-2.0，可本地 Docker 自托管）的真实 trace 一致。真实埋点方式是把 ctx.trace.span() 换成 Opik 的 span API，LangGraph 侧用官方的 OpikTracer / track_langgraph 包裹一次即可。


          
容易写反的地方

          
Opik 的 MCP 能力是「它自己作为 MCP server」供编码 agent 读取 trace，不是追踪 MCP 调用。本页的 MCP 工具 span 是 Harness 自己埋的，不依赖 Opik 的 MCP 功能。


          
为什么不选更重的方案

          
Langfuse 自托管需要 postgres + clickhouse + redis + minio 五个服务，对一个作品集是过度工程；Phoenix 的 Elastic License 2.0 非 OSI 认证；OpenLLMetry 只是 instrumentation 库集合，本身没有后端，不解决「要有一个能截图的 trace 面板」。

        

      


      

        
取舍评估过但没选，以及为什么

        

          
MCP 网关（docker/mcp-gateway、IBM ContextForge、stacklok/toolhive）

          
我读过 docker/mcp-gateway 的源码，它其实有两层：isToolEnabled() 只过滤 tools/list（让模型看不见），而 withInvokePolicy() 作用在 mcp.CallToolRequest 上、fail-closed，direct call / mcp-exec / code-mode 三条路径共用。但 NewDefaultClient() 在不在 Docker Desktop、或 MCPGovernance 特性未开时返回 NoopClient（恒放行），而且 policy.Request 只有 {server, tool, action, workingSet}——拿不到 ctx、会话状态与业务规则。所以它能做调用期拦截，但默认是关的，且判不了业务，只能当纵深防御的第二道。


          
AG-XGuard

          
cage 三引擎（json_schema / regex / forbidden_string）形态最接近 deterministic_validator，severity 三档（BLOCK / WARN / ROLLBACK）的设计直接借鉴了它。但它在 PyPI 上没有分发，只能 git clone，且两个核心能力（StructuralPatch / ROLLBACK）作者自己标注未实现。抄设计，不引依赖。


          
AEH（agentic-engineering-harness）

          
主张「模型输出不能选工具、不能授权、不能验收」——与本文立场几乎逐字相同。但它自带一整套 L1–L5（58.5 MB、3578 files、依赖 Paseo / mise / OpenSpec），是竞品不是零件，其 validator 无法作为库抽出复用。


          
AiWrangler

          
HUMAN REVIEW 的批准通道设计值得抄——它明确「agent 的 tool arguments 永远不构成批准」，批准只能来自 MCP elicitation、原生桌面弹窗或 TTY 里人手动输入。但它核心判定依赖 TypeSafe 的 Jev 商业模型，diff 与 spec 会外发。只抄审批通道的形态。


          
Remotion MCP

          
官方已废弃（最晚 2026-08-31 关停），理由之一是「agents do not invoke them reliably」。Remotion 的正确用法是被 Harness 调度的 SSR API（bundle → selectComposition → renderMedia），包成受管工具后落进 L1–L4，而不是当成一个 MCP 技能。

        

      

    

  


  
  

    

      

        我知道大模型会幻觉、会漂移、会在你没注意的时候

        把一次 8 万块 的写入执行成 840 万。
      


      

        

          这不是模型变差了，是它本来就这样——概率系统天生不会为「确定」负责。
          指望下一代模型自己变可靠，等于把工程问题押在一次训练更新上。
        

        

          我的做法反过来：不要求模型可靠，要求系统可靠。
          模型只负责生成候选，能不能落地由代码判定；判定不过就带着失败现场重来；重来太多次就停手叫人。
          这套结构在换模型、换供应商、换 Prompt 之后依然成立——因为它管的是流程，不是某一个模型。
        

        

          所以这个作品想证明的不是「我很会用 AI」，而是：
          我能把玩具级的 AI 改造成生产环境里可验收、可审计、可回滚的系统。
          这条能力线，恰好也是我做企业交付这些年一直在做的事——只是把「验收标准」从人嘴里搬进了代码里。
        

      


      
    
        
  • 
          驾驭
          五层结构把「模型想做什么」和「系统允许做什么」拆开，中间那层是代码，不是提示词。
        
    • 
        
  • 
          验收
          交付标准写成了断言：测试、Schema、业务规则、CI 门禁。过不了就是没过，没有「差不多」。
        
    • 
        
  • 
          可复制
          四个函数、一份策略表、一条 CI 流水线。换一个业务域，改的是规则库，不是引擎。
        
    • 
      


      

        一句话收口：
        真正拉开工程能力差距的，从来不是选了哪个模型，而是你有没有一层能把「不确定」变成「可验收」的结构。
        模型会继续变强，但这层结构不会因此变得不必要——它只会变得更值钱。
